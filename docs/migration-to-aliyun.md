# 阿里云海外服务器迁移评估与方案

评估日期：2026-10-29。源项目：`/home/ubuntu/grindbuddy`。

本次交付是评估与执行方案，未停止源服务、未修改生产配置、未执行数据库恢复。下述自动化流程是待实现的脚本要求，不代表仓库已有可运行的一键迁移脚本。

## 1. 结论与适用条件

**按当前数据量与低负载状态，2 核、2 GB 内存、40 GB 系统盘的服务器可以承载这个程序及数据库。建议用“现有镜像离线搬运 + PostgreSQL 逻辑备份恢复”，不要在新机重新构建，不要直接复制数据库目录。**

用户已确认：

- 搬迁程序运行全套：数据库、配置、全部现有 Docker 镜像、源码、历史备份。
- 不搬迁 VS Code 等宿主机开发工具；应用运行必需的 Python、uv、Python 依赖、Nginx 已在镜像内。
- 允许短暂停机，优先保证不丢数据。
- 新机仅已知 Docker 26.1.3、2 核 2 GB、40 GB 系统盘、200M；系统、架构及带宽具体含义尚未确认。

可行性仍有三个执行前提：

1. 新机是可正常运行 Linux 容器的 **x86_64/amd64** 系统，建议 Ubuntu 24.04 LTS。现有镜像全部为 `linux/amd64`；如果新机是 ARM，不属于原样离线搬迁，需要重新构建匹配架构的镜像并重新演练。
2. Docker 26.1.3 能正常启动，且另外安装了可解析本项目配置的 **Compose v2 插件**。Docker 版本号不代表自带 Compose。镜像载入、PostgreSQL 启动和恢复必须在该新机实测通过。
3. 业务主要是少量用户、常规进销存操作。此次读到的是资源快照，不是并发压测，不能据此承诺大并发或批量报表峰值性能。

“200M”暂按公网带宽 200 Mbps 理解，理论单向上限约 25 MB/s，并非 200 MB/s，也不代表持续保证值。传输速度还受源机上行、跨境链路及限额影响。若它指 200 MB 流量配额，则远不足以搬迁镜像，需先确认套餐。

业务记录快照：用户 2、客户 81、供应商 17、商品 63、库存余额 63、库存流水 81、采购单 27、采购退货单 5、销售单 19。这里只作为当前量级参考，正式验收必须使用最终停写后重新生成的基准，不能硬编码这些数字。

已确认：

- 只有三个应用容器；数据库未映射公网端口，前端映射宿主机 `8080`。
- PostgreSQL 卷挂载到 `/var/lib/postgresql`，实际数据库目录为 `/var/lib/postgresql/18/docker`。这是当前 PostgreSQL 18 镜像的布局，不要改成旧版常见的卷挂载路径。
- 后端与前端无文件持久卷；源码未发现文件上传字段或独立对象存储依赖，容器可写层未发现业务文件。
- 未发现 Redis、Celery、宿主机 PostgreSQL、独立宿主机 Nginx/TLS 服务或项目关联定时任务。云厂商代理及其定时任务不是应用依赖，不搬到阿里云。
- 根 `.env` 保存生产密钥、数据库配置、访问地址和端口；SMTP 当前未配置，迁移不会自动获得邮件找回密码能力。
- 除当前应用用户外无额外非系统数据库角色；维护库 `postgres` 无用户表；没有 large object，扩展只有 `plpgsql`。若正式执行时盘点变化，必须扩大备份范围并停止按此简化假设执行。
- 已执行 `pg_dump -Fc` 到管道，并用 `pg_restore --exit-on-error --file=/dev/null` 完整读取，两个命令退出码均为 0。该检查不执行 SQL 恢复、未落盘业务备份，**不等于已验证新机真实恢复成功**。

## 3. 资源安排

### 内存与 CPU

- 保留现有两个 Gunicorn worker，迁移时不同时调整应用行为。
- 运行机不执行 `npm ci`、`npm run build`、`uv sync` 或镜像构建；前端构建产物和后端依赖随现有镜像导入。
- 建议新机有约 2 GB swap 作为偶发峰值保护；先检查已有 swap，不能覆盖已有文件或重复写入启动配置。swap 不替代物理内存。
- 不常驻 VS Code Remote、开发服务器或构建任务。源机 VS Code 文件本身约 3.4 GB，不在此次迁移范围内。
- 迁移阶段不盲目设置过小容器内存限制，不关闭 PostgreSQL 的 `fsync`、`synchronous_commit`、`full_page_writes`。
- 真实恢复、登录、常用查询与报表验证时观察容器内存、宿主机可用内存、swap 和 OOM 记录。持续内存紧张或频繁换页，则升至 4 GB，不以健康接口返回成功代替容量验收。

### 磁盘

40 GB 按现有体量够用，但要同时容纳系统、Docker 镜像、迁移压缩包、解包目录、数据库、swap、日志和后续备份。

- 目标系统及 Docker 安装完成后，建议至少还有 **15 GiB 可用空间**作为此次小规模迁移的保守下限。
- 最终脚本仍须按实际包大小、解压空间、镜像导入空间及安全余量重新计算；15 GiB 不是任意未来数据量的保证值。
- 现有容器使用 `json-file` 日志且没有轮转配置。目标容器建议配置每个日志文件 `10m`、最多 `3` 份，防止长期耗尽系统盘。
- 初期保留全部迁入镜像和备份，验收后再单独制定保留策略；不得自动执行镜像或卷清理。
- 不把只存在新机系统盘中的备份当成灾备，需另存受控的异机/离线副本。

## 4. 迁移范围

| 对象 | 迁移方式 |
| --- | --- |
| 正在运行的前端、后端和 PostgreSQL | 记录运行容器实际镜像 ID，以 `docker image save` 导出并在新机 `docker image load` |
| 全部其他本地镜像 | 导出所有仓库标签；另外导出无标签镜像 ID，保留 ID/标签清单并逐项核对，不能只导出三个在用镜像 |
| 源码、锁文件、migrations、Compose、Nginx 配置、隐藏配置文件 | 源项目归档；保留 Git 信息及现有历史备份，禁止漏掉根 `.env` |
| 当前业务数据、账号密码哈希、库存、单据、约束、序列 | 同版本 PostgreSQL 18.6 的自定义格式逻辑备份与恢复，不使用 Django fixture 代替 |
| 数据库角色/其他数据库/非默认权限 | 正式盘点；当前可由相同 `.env` 初始化应用角色。若新增对象，补充全局对象及其他数据库的受控备份恢复 |
| 密钥与凭据 | 同一生产环境搬家，受控复制并维持原值；访问地址按新机或原域名调整，切勿重新生成 Django 密钥后再声称原样迁移 |
| Docker 网络与卷 | 根据迁移配置在目标重新创建，不复制容器内部 IP 或 Docker 内部目录 |
| Docker daemon 配置 | 盘点并留档，按目标平台核对适用项。源机有镜像加速配置，不原样覆盖目标已有配置或带入源云厂商专用地址 |
| 宿主机 Python、Node、uv、VS Code、云代理、SSH 主机密钥 | 不复制；运行所需部分已包含在容器镜像。新机保留自己的系统、网络与安全身份 |

禁止以 `docker export/import` 代替镜像 save/load，前者不是完整保留镜像配置的迁移方法。也不复制 `/var/lib/docker` 或在线 PostgreSQL 数据目录。

镜像导入使用普通 save/load，不依赖新版本才支持的 `--platform` 等选项。Docker 官方提供镜像归档机制，但跨版本落地是否成功仍以目标 Docker 26.1.3 的实测为准。

## 5. 推荐流程：预传演练 + 短暂停写最终切换

### 阶段 A：目标准备及在线预传，不影响旧系统使用

1. 在新机检查系统、架构、内核、磁盘、Docker、Compose、时间同步、SSH 和端口占用；不满足条件即退出。
2. 阿里云安全组及主机防火墙放行必要的 SSH 和业务端口。迁移与演练期间业务端口只允许受控来源；数据库 `5432`、后端 `8000` 不开放公网。
3. 源机生成镜像 ID/标签清单、项目归档和已安装服务配置清单，导出全部镜像。
4. 归档目录采用最小访问权限；通过经过主机指纹确认的 SSH 传输。敏感包如需落到其他存储，先加密；不在聊天、命令日志中输出密钥和密码。
5. 校验 SHA-256。校验清单必须从可信 SSH 通道取得；散列用于检测损坏，不能代替身份认证或加密。
6. 在线生成一份演练数据库备份，在新机独立项目、独立卷、受限入口中真实恢复；不覆盖任何已有目标数据。
7. 核对同版本镜像、数据库、约束、序列、migrations、业务读取和资源占用。在线演练期间源库仍在变化，因此不能把演练库直接当最终库切流。
8. 演练成功后保留报告；最终恢复必须使用新的空卷/空目标，不能向演练数据库反复覆盖式灌入。

**此阶段提前完成大镜像传输，正式停机期间只传很小的最终数据库备份和变更文件。**

### 阶段 B：批准维护窗口，冻结旧系统写入

1. 固定本次版本，期间禁止部署、修改配置、镜像清理或直接操作数据库。
2. 记录源系统状态，阻止新业务请求，优雅停止前端和后端，并等待已有请求/事务完成；不停止数据库。
3. 确认不存在其他写入客户端、后台任务或人工 SQL 写入。不满足则不做最终备份。
4. 使用正在运行的 PostgreSQL 18.6 容器执行最终 `pg_dump -Fc`。必须启用失败即停止及管道错误传播，检查退出码、文件非空和归档可完整读取。
5. 在持续停写状态下生成最终验收基准：所有应用表的精确行数、确定性排序后的全表内容摘要、序列状态、约束/索引和迁移记录。日期、时区、编码及排序方式必须固定；不能只比较总行数。
6. 对最终备份及基准生成 SHA-256，受控传输到目标；源机继续保持应用停止，不自动恢复写入。

短暂停机窗口可先按 **5–15 分钟**安排，但这是规划值，不是实测承诺。最终以新机演练结果、链路和验收耗时修订；如果希望停机期包含人工全面验收，应预留更长时间。

### 阶段 C：目标恢复、验证，不开放业务写入

1. 再次验证文件 SHA-256、清单、镜像 ID、目标架构及磁盘空间。
2. 使用明确命名的全新项目和全新卷；若同名目标已存在或发现任何已有业务数据，立即停止并要求人工处理，不能自动清空。
3. 用源机相同 PostgreSQL 18.6 镜像、角色、密码、数据库名、编码及兼容的 locale 初始化。卷维持 `/var/lib/postgresql` 挂载方式。
4. 仅启动数据库，使用 `pg_restore` 的遇错退出模式恢复；在适合本次恢复参数时使用单事务。不得忽略错误继续启动，不对已有业务库执行覆盖式恢复。
5. **先验证数据库，再启动后端。** 原启动命令会自动执行 `migrate`，因此必须确认对应镜像和数据库迁移版本一致、没有意外待执行迁移，防止迁移搬家同时升级结构。
6. 比对所有表精确行数、全部内容摘要、序列 `last_value/is_called`、约束/索引、49 条迁移记录对应的最终基准；当前快照数字不作为固定要求。
7. 原 `.env` 只更改访问地址相关项：按需增加新 IP/域名至 `DJANGO_ALLOWED_HOSTS`，调整 `CORS_ALLOWED_ORIGINS`，如配置了找回密码则调整链接域名。保留数据库身份、密码和 Django 密钥；不直接执行 `source .env`。
8. 明确给前后端指定已加载镜像名称，禁止镜像拉取及构建，防止 Compose 因项目名变化找不到默认生成的镜像标签。目标启动需等效于 `up -d --no-build --pull never`，不能只运行 `up --build`。
9. 先保持入口受限，通过 `/api/v1/health/`、数据库真实查询和原账号登录验证。健康接口当前不查询数据库，单独返回 `ok` 不能证明恢复成功。
10. 检查库存、客户、供应商、采购、销售、报表、权限、序列和单据编号；重启目标容器后重新检查数据持久性。

验收前不进行会污染最终库的注册、新建单据或删除操作；写入型演练应在阶段 A 的独立演练库中完成。若在最终库进行了写入，即使只是测试，也必须按“目标已写入”规则处理回退。

### 阶段 D：单点切流

1. 确认全部自动校验与人工验收通过，才开放新机入口或修改域名解析。
2. 使用域名时提前调整 DNS TTL，并等待旧缓存消退。旧服务器的应用继续停止，不能因为仍有旧 DNS 请求就恢复成另一套可写库。
3. 使用 IP 直接访问时更新访问地址；HTTP 的现有部署不因迁移自动变成 HTTPS，证书部署如需要应另行明确。
4. 新机成为唯一写入点，监控日志、资源、数据库错误和用户反馈。
5. 源机保留至少 7 天或按业务确认的保留期封存；最终备份、校验清单另存受控副本。确认前不删除源卷、原备份或释放旧服务器。

## 6. “一键”的合理边界

建议实现为 **两端各一条主命令，带演练和人工确认关卡**，而不是把新机密码写进一个跨机脚本：

| 操作 | 自动化职责 | 必须停止的情况 |
| --- | --- | --- |
| 源端 prepare | 只读盘点、全镜像导出、源码/配置/历史备份归档、散列清单；可不停业务 | 空间不足、运行镜像不在导出清单、归档或传输失败 |
| 目标 rehearsal | 预检查、校验、载入、独立演练恢复及对账 | 架构/Compose 不满足、镜像不能启动、已有目标冲突、恢复或校验失败 |
| 源端 finalize | 明确确认后停写、最终备份、最终内容/序列基准、传输 | 有其他写入、备份失败、完整读取失败、传输校验失败 |
| 目标 restore | 新空卷恢复、数据对账、受限启动及报告 | 数据不一致、意外待执行迁移、端口冲突、服务不健康 |
| cutover | 展示检查结果并等待确认后开放入口 | 任一检查未通过，或旧端写入状态不明确 |

自动化实现还须满足：

- 默认不停止业务，停写阶段必须明确选择；失败退出时报告源端是否仍停止，不能以“成功”掩盖半成品。
- 不生成或显示凭据，不把展开了密码的 Compose 完整配置保存到普通日志。
- 不覆盖现有数据库/卷，不执行 `down -v`、`volume rm`、`system prune`、覆盖恢复或自动清理源数据。
- 防止重复运行和并发执行；中断后默认停止并报告状态，不在不清楚备份对应版本时盲目续跑。
- 不在失败处理里无条件重启旧后端；只有确定新端从未接受写入且入口已关闭，才能走回退。
- 镜像大包先预传，最终停写时仅补传变更文件；失败可以安全重传，但备份与基准必须保持同一批次。
- 显示最终“已验证恢复”或“仅完成导出/演练”等真实状态，不能把容器启动当成迁移成功。

仓库当前 `infra/scripts/` 只有脚本规范，明确要求实现前确认备份保留、恢复授权和停机窗口。本方案已确认允许短暂停机；**正式脚本编写及运行前仍需确认目标系统/架构、目标目录、连接方式、切流入口及保留期。**

## 7. 不丢数据与回退

这里的目标是：**在完整冻结全部写入、最终备份恢复成功并通过对账、仅开放新机单点写入的前提下，迁移切换 RPO 为 0。** 单机迁移不能保证硬盘永久不坏、无人误删或灾难下绝不丢数据；后续仍需要异机备份和恢复演练。

### 新机从未接受业务写入

关闭并隔离新机入口，确认没有目标端新增数据，再启动原前后端并恢复旧入口。源库一直保留，不需要将演练或失败恢复结果写回源库。

### 新机已经接受任何写入

不能直接改回旧 IP/域名并启动旧库，否则新机新增单据和库存变更会丢失。必须：

1. 再次冻结新机写入；
2. 对新机当前完整数据库做最终备份及对账基准；
3. 备份并保留旧库，向受控的新目标恢复新机数据，而不是盲目覆盖旧库；
4. 完成同等级别验证后再反向切流。

恢复失败、网络中断或超时，优先维持维护状态并保留两端数据，不自动双端开放。

## 8. 执行前及交付验收清单

- [ ] 确认新机 OS、x86_64/amd64 架构、Docker 26.1.3 和 Compose v2 实际输出。
- [ ] 确认“200M”是带宽而非流量配额，确认跨境访问体验和安全组。
- [ ] 确认目标目录、SSH 主机指纹、操作者恢复权限和备份保存位置，不在聊天中索取密码或私钥。
- [ ] 确认源端最终停写时间、旧机保留期、切流方式及出问题时谁批准回退。
- [ ] 全部源镜像 ID/标签清单完成比对，三个运行镜像没有被重新构建替换。
- [ ] 源码、隐藏配置、历史备份、最终全量备份均已校验。
- [ ] 在新机实际完成恢复演练，恢复命令及全部校验退出码为 0。
- [ ] 正式切换后业务表内容、序列、约束、索引、迁移记录与最终停写基准一致。
- [ ] 原账号登录、关键业务读取、容器重启后的数据持久性与资源检查通过。
- [ ] 全程只有一个可写业务入口，旧机与异机备份保持完整。
