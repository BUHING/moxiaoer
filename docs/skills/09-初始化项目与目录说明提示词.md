## 目录和架构约束
- Django app 内部按项目现有约定组织；新 app 至少应预留 `models.py`、`serializers.py`、`views.py`、`urls.py`、`services.py`、`permissions.py`、`tests/` 等清晰位置。没有实际逻辑时不得生成大量空壳文件；应放置最少必要的 `__init__.py` 和明确的说明。
- 库存、单据审核、作废、退货、盘点和调拨的核心写操作将来必须进入后端 service/use-case 层，不能放进 View、Serializer 或前端。
- 前端 `features/` 必须按业务模块隔离；一个模块的页面、局部组件、queries 与表单逻辑优先放在该 feature 内。
- `frontend/src/api/` 的生成文件与手工请求配置要明确区分。生成目录不要混入手写代码。
- `docs/` 是功能范围、最终系统设计、业务规则和 API 契约的唯一文档位置；避免在代码注释中复制整份规则。`docs/功能模块设计.docx` 决定首期范围，`docs/system-design.md` 确认后决定技术设计细节。
- 不创建微服务、消息队列、Redis、Celery、Kubernetes、移动端项目或多余 UI 框架，除非已有规格明确要求。
- 严禁将密钥、数据库密码、JWT 密钥或真实连接信息写入仓库；所有示例使用安全占位符。
- `.gitignore` 应忽略 Python 虚拟环境、缓存、前端依赖、构建产物、环境变量文件、测试覆盖率和本地数据库文件，但保留 `.env.example`。

## 最小可运行骨架
请使用生态工具实际初始化，而非手工伪造配置：
1. 选择并说明一个 Python 包管理器；优先使用 `uv`，若当前环境不可用则使用项目中已有的替代方案。不要同时引入多种包管理方式。
2. 初始化 Django 项目和最小 DRF 配置，配置 `/api/v1/` API 根路径、健康检查端点、drf-spectacular Schema/Swagger 入口、JWT 基础认证配置，以及开发环境 CORS 配置。
3. 初始化 Vue 3 + TypeScript + Vite 项目，安装并接入 Element Plus、Pinia、Axios、TanStack Query for Vue；建立基础路由、布局、认证状态和 API Client 生成配置的目录边界。
4. 创建用于运行机的 PostgreSQL、backend、frontend Docker Compose 服务和安全的 `.env.example`；镜像标签必须与 `ENVIRONMENT_BASELINE.md` 一致。开发机的后端与前端启动不得依赖 Docker，且开发机数据库主机必须可配置为 `127.0.0.1`。
5. 建立 pytest、pytest-django、Ruff 的最小配置与一个可运行的健康检查测试。前端测试仅在初始化时已有合适工具链时配置；不要为了占位引入不必要的测试工具。
6. 在不编造业务规则的前提下，为各业务 app/feature 创建清晰的边界和最少必要的初始化文件。
7. 更新 README.md：技术栈、目录、启动前置条件、实际可执行的启动/迁移/测试/lint 命令，以及后续开发应先阅读功能模块设计、系统设计说明书和关联 docs 的规则。

## `DIRECTORY_STRUCTURE.md` 的强制内容
该文件必须直接位于项目根目录，且使用中文编写，至少包含：
1. “目录树”章节：以实际创建后的目录树为准，不能照抄未创建的结构；忽略 `node_modules`、`.venv`、缓存、构建产物和其他生成依赖。
2. “根目录文件说明”章节：说明 README、Compose、环境变量、代码规范、文档等关键文件。
3. “后端结构说明”章节：逐一说明 `config`、每个业务 app、测试、迁移、依赖和环境配置的位置与职责。
4. “前端结构说明”章节：说明 `api`、`features`、通用组件、路由、stores、样式、测试和生成代码边界。
5. “文档与基础设施说明”章节：说明 `docs`、`infra/nginx`、`infra/scripts`。
6. “模块放置规则”章节：新增后端 app、API、业务服务、前端 feature、通用组件、测试、迁移、脚本和规格文档分别应放在哪里。
7. “禁止事项”章节：包括不要直接修改生成 API Client、不要在 View 中堆业务规则、不要直接改库存余额、不要提交 `.env` 和密钥。
8. “更新规则”章节：目录结构改变时必须同步更新本文件；新增或调整功能范围时先更新 `docs/功能模块设计.docx`，再同步更新 `docs/system-design.md`、业务规则、API 和关联 `docs/` 文件。

- 验证 Docker Compose 配置可解析；若开发机未安装 Docker，不得尝试安装或运行 Docker，应明确记录只完成静态配置校验的限制。
- 验证后端依赖、Django 系统检查、迁移检查/健康检查测试和 Ruff。
- 验证前端依赖安装、TypeScript 检查或构建（以脚手架实际提供的命令为准）。
- 若环境无法运行某个命令，明确记录具体阻塞原因、已完成的部分和用户需要执行的最小后续步骤；不得假称已通过。

## 使用顺序

建议先确认 `docs/功能模块设计.docx`，再让 AI 依次生成并确认 `docs/requirements.md`、`docs/domain-rules.md`、`docs/data-model.md`、`docs/api.md`、`docs/ui.md`、`docs/acceptance.md` 和 `docs/system-design.md`，最后使用本提示词初始化代码仓库。若想先创建骨架，也可直接使用本提示词；后续系统设计说明书和规格文档完成后，再按 `08-模块开发提示词模板.md` 逐模块开发。
