# 生成 `docs/system-design.md` 的提示词

```text
你是一名资深系统架构师、领域建模师和 PostgreSQL 数据库架构师。请为磨小二进销存系统生成完整的最终系统设计说明书，并只输出 Markdown 正文。输出将原样保存为 `docs/system-design.md`。不要输出 Django Model 代码、SQL migration、前端组件代码、实现代码或寒暄。

## 输入文档与优先级
请先完整阅读以下文档：
1. `docs/功能模块设计.docx`：功能范围主文档。其文字描述是首期功能、账号体系、角色权限、业务流程和用户可见名称的首要依据；其中参考图仅用于理解交互意图，不能覆盖文字说明或增加功能。
2. `docs/requirements.md`：将功能模块设计转写为可验收的需求规格。
3. `docs/domain-rules.md`：库存、金额、状态、权限、审计和并发等不可违反规则。
4. `docs/data-model.md`：实体、字段、关系、约束和索引建议。
5. `docs/api.md`：前后端 API 契约和关键动作语义。
6. `docs/ui.md`：页面、状态驱动交互和权限展示要求。
7. `docs/acceptance.md`：验收场景和发布准入要求。

本说明书是上述文档经一致性核对和收敛后的最终系统设计基线，用于指导项目初始化、数据库迁移、后端服务、API、前端和测试。

## 一致性与范围规则
- 只设计功能模块设计中明确的首期功能。商品规格、商品属性、价格等级、商品价格、客户、供应商、进货、销售、退货、库存查询、统计分析、员工管理、角色权限和店铺信息等，应按主文档实际描述设计。
- 仓库、盘点、调拨、库存预警、导出、手机号登录/注册、短信服务、操作日志、备份恢复、税务、批次、序列号和保质期等，仅在主文档或已确认上游规格明确纳入时设计为首期能力；否则列为后续预留、范围外或待确认，不能悄悄纳入。
- 必须保持 boss 账号数据隔离、employee 账号由所属 boss 创建、权限由 boss 授予或审批、默认权限和授权申请等已确认规则；任何与上游规格不一致的地方都必须显式列出。
- 主文档与上游文档出现矛盾、缺少字段定义、缺少状态或无法确定的技术选择时，不得自行选定。写入“待确认事项”，包括来源、冲突或缺口、受影响的模块/表/API、可选方案和推荐方案。在未确认前，不得将该方案标为最终决定。
- 金额使用 PostgreSQL `numeric` 和后端 `Decimal`，JSON 中以字符串传输；禁止 float。所有库存、金额和单据状态变更必须在数据库事务中完成。库存不能被普通 CRUD 直接修改，每次变动必须保留可追溯流水。

## 输出结构
使用以下章节组织文档。内容应足以让开发人员直接拆分 Django migration、service、DRF API、Vue feature 和自动化测试任务，但不要生成这些实现代码。

1. 文档目的、读者与设计范围
   - 说明本说明书与功能模块设计及各分领域规格的关系、输入版本或状态、首期范围、后续预留和明确范围外内容。

2. 系统概览与架构设计
   - 描述单体后端加独立前端的逻辑架构、主要模块边界、外部依赖、数据流和部署边界。
   - 使用 Mermaid 绘制系统上下文图和容器/组件级架构图，展示开发机原生 Vue 3、Django REST Framework、PostgreSQL、JWT、OpenAPI 与运行机 Docker Compose 的关系；开发机不安装 Docker，运行镜像版本以根目录 `ENVIRONMENT_BASELINE.md` 为准。
   - 列出关键非功能设计：认证授权、租户隔离、审计、事务、并发、错误处理、时区、备份恢复边界和可观测性；未确认项单列，不得伪造方案。

3. 业务与模块设计
   - 按功能模块设计的模块顺序描述每个首期模块的职责、用户、输入、输出、依赖模块、关键业务流程、权限边界和范围限制。
   - 给出模块依赖图；明确数据归属和禁止跨模块直接写入的数据。
   - 汇总账号、角色、权限和数据隔离模型，特别说明 boss 与 employee 的生命周期、所属关系、默认权限、授权申请和审批边界。

4. 概念设计
   - 定义核心业务概念、聚合或实体、值对象及它们的职责；术语必须与功能模块设计一致。
   - 使用 Mermaid ER 图展示全部首期核心实体、实体间基数和关键关系，图外提供完整文字关系说明。
   - 标出租户/组织边界、账号归属、商品资料、价格体系、业务单据、库存余额/流水、统计来源以及审计对象。不得把尚未确认模块伪装为已确定实体。

5. 逻辑设计
   - 按模块给出逻辑表/实体清单。每张表至少说明：逻辑名称、建议物理表名、用途、所属模块、主键、租户归属、核心业务属性、派生属性、不可变属性、来源或计算规则。
   - 为每个关系列出父子关系、基数、必填性、外键语义、删除/停用策略和历史追溯要求。
   - 定义关键枚举、状态机、单据编号、金额/数量精度、价格选择、初始库存、库存流水方向和统计口径。通过决策表或状态转换表说明库存增加、减少、金额影响和失败结果。
   - 说明规范化策略与有意保留的冗余字段，以及库存余额与库存流水如何避免双写漂移。

6. 数据库设计
   - 以 PostgreSQL 为目标，逐表给出物理结构。每张表使用表格列出：字段名、中文含义、PostgreSQL 类型/长度/精度、可空性、默认值、是否主键/外键、是否由后端计算、校验规则、敏感性和备注。
   - 逐表列出唯一约束、Check 约束、外键及其删除行为、索引（字段、类型、唯一性、服务的查询或一致性需求）。
   - 明确公共审计字段、软删除或停用字段、创建/更新时间的时区策略，以及所有业务数据如何强制关联并按 boss 隔离。
   - 对库存余额更新、库存流水写入、单据审核/作废、并发出库等关键写操作说明事务边界、行锁或等价并发控制、幂等键和失败回滚要求。
   - 说明数据迁移、初始字典数据、备份恢复和数据保留的设计边界；没有确认策略时列入待确认事项。

7. 接口与界面实现约束
   - 汇总与数据模型强关联的 API 资源、专用业务动作、只读计算字段、权限和涉及的领域规则编号；以 `docs/api.md` 为准，不重复完整接口清单。
   - 汇总模块页面、路由、状态驱动操作、页面数据来源与关键校验；以 `docs/ui.md` 为准，不复制完整 UI 规格。
   - 说明 OpenAPI 到 TypeScript Client 的生成边界，禁止手工维护重复 DTO。

8. 关键流程与一致性设计
   - 为注册/登录、员工创建与授权、商品建档与价格维护、进货入库及退货、销售出库及退货、库存查询、首页关键数据和统计，给出时序图或流程图及文字说明。
   - 每个流程必须标出权限检查、租户过滤、状态前置条件、事务边界、库存/金额影响、审计记录和幂等处理。
   - 只有在已确认范围内时才设计盘点、调拨等流程。

9. 安全、权限与审计设计
   - 说明 JWT 会话边界、密码安全、最小权限、前后端双重权限控制、对象级租户校验、敏感数据展示和操作审计要求。
   - 列出主要威胁或误用场景及对应控制措施，包括越权读取、跨 boss 数据访问、重复提交、并发超卖和直接篡改库存。

10. 测试与追溯矩阵
    - 建立“功能模块 -> 需求 -> 领域规则 -> 逻辑/物理表 -> API/页面 -> 验收用例”的追溯矩阵。
    - 列出 P0 一致性测试：租户隔离、权限拒绝、库存余额与流水一致、金额精度、重复动作幂等、事务回滚、并发出库。

11. 待确认事项与变更管理
    - 汇总所有未决事项及推荐方案，不得遗漏输入文档中已有的待确认项。
    - 定义变更影响规则：功能范围变化先更新 `docs/功能模块设计.docx`；已确认的实体、关系、表或约束变化同步更新本说明书、`docs/data-model.md`、`docs/domain-rules.md`、`docs/api.md`、`docs/ui.md` 和 `docs/acceptance.md` 中受影响部分。

## 质量要求
- 使用清晰、可审查的中文。所有表、关系、枚举、状态和约束必须有稳定名称；领域规则继续引用已有规则编号，缺少编号时标注待补充而不是临时编造相互矛盾的编号。
- Mermaid 图必须能独立阅读，不能只用图替代文字说明。
- 明确区分“已确认设计”“后续预留”“范围外”和“待确认事项”。
- 输出前执行内部一致性检查：首期模块是否逐一覆盖；每个库存/金额动作是否有状态、权限、事务和流水设计；每张业务表是否有租户隔离、主键、审计和约束说明；任何未确认内容是否没有被写成既定事实。
```
