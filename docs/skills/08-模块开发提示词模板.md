将下面代码块完整复制给 AI，并替换所有 `[方括号]` 内容。若某项不适用，明确写“无”；不要删除约束。

```text
你是一名资深全栈工程师。请在当前仓库内完整实现“[模块名称]”模块。先阅读 `docs/功能模块设计.docx`（功能范围主文档）、`docs/system-design.md`（最终技术设计基线）、提供的关联规格、现有代码和项目约定；确认实现路径后直接修改代码并完成与该模块相关的验证。不要重构无关模块，不要改变既有 API 契约或领域规则。

## 必须阅读的现有代码
请先根据仓库实际结构定位并阅读以下内容；找不到时说明原因，不要凭空假设文件路径：
- 后端项目配置、依赖清单、URL 路由、认证/权限配置、统一异常处理、分页与过滤配置。
- 与本模块相关的 Django app：models、migrations、serializers、views/viewsets、services、permissions、tests。
- 与库存、金额、单据状态或审计相关的共享服务、工具和测试。
- 前端项目配置、路由、Pinia stores、API Client/OpenAPI 生成配置、通用请求错误处理、鉴权路由守卫。
- 与本模块相关的 Vue feature：页面、组件、composables、查询键、类型、测试。
- 根目录 `ENVIRONMENT_BASELINE.md`、`.python-version`、`.nvmrc`、环境变量示例、运行机 Docker Compose，以及项目实际配置的 lint/test 命令。

## 实现约束
### 后端
- 使用 Django、Django REST Framework、PostgreSQL 和现有项目模式；业务逻辑不能堆放在 View 或 Serializer 中，应放入清晰的 service/use-case 层。
- 开发机不安装 Docker，使用本机 PostgreSQL；运行机 Dockerfile 与 Compose 必须继续使用环境基线规定的固定基础镜像及锁文件，不能漂移版本。
- 严格遵循 docs/api.md；API 根路径、响应格式、错误格式、分页、筛选、排序和权限与既有规范一致。
- 所有金额使用 Python Decimal 和 PostgreSQL numeric；请求/响应中的金额与高精度数量遵循既有字符串格式，禁止使用 float。
- 任何库存、单据状态或金额变更都必须在数据库事务内进行；必要时采用已有锁机制，避免并发造成超卖或重复入库。
- 禁止提供“直接改库存余额”的普通 CRUD 接口。库存变化必须经由已定义的业务动作并创建可追溯的库存流水。
- 审核、作废、反审核及其他状态动作必须幂等；重复请求不能重复产生库存或金额影响。
- 后端必须强制检查权限，不能依赖前端隐藏按钮；所有验证失败应返回项目约定的明确错误。
- 不删除或破坏已有数据迁移。模型变更必须创建规范的 Django migration；已有业务引用的基础资料遵循停用/删除规则。
- 不使用 `as any`、`# type: ignore`、吞掉异常的 broad catch、静默 fallback 或未解释的类型绕过。

### 前端
- 使用 Vue 3、TypeScript、Element Plus、Pinia、Axios 和 TanStack Query for Vue，并遵循现有目录和命名模式。
- 只使用 OpenAPI 生成的类型和 API Client；禁止手写一份与后端重复的 DTO 类型或请求代码。
- 使用查询缓存和清晰的 query key；完成创建、审核、作废等 mutation 后，准确失效相关列表、详情和库存查询缓存。
- 表单必须实现规格要求的前端即时校验，并正确展示后端字段错误和业务规则错误。
- 按单据状态与权限控制按钮和字段的可见/可编辑性；这只用于用户体验，不能替代后端校验。
- 处理加载、空数据、请求失败、无权限及危险操作二次确认。
- 不引入新 UI 框架、状态管理库、请求库或大型依赖，除非本任务明确要求且先说明理由。

## 交付内容
1. 完成本模块所需的后端、前端、迁移和必要文档更新。
2. 如 API 契约有经过确认的增量，更新 drf-spectacular/OpenAPI 定义，并重新生成前端类型/API Client；不要手动修改生成物之外的重复定义。
3. 为高风险业务规则补充自动化测试，至少覆盖：
   - 成功路径；
   - 权限拒绝；
   - 参数或状态非法；
   - 重复动作的幂等性；
   - 事务失败回滚；
   - 涉及库存时的库存余额和库存流水一致性。
4. 如涉及页面，完成对应表格、筛选、表单、详情及错误反馈，并为关键流程补充项目已配置的前端测试。
5. 运行仓库已有的、与改动范围最匹配的迁移检查、后端测试、前端测试、类型检查和 lint 命令；修复本次改动引入的问题。

- [ ] 实现与本次任务范围完全一致，没有夹带无关重构。
- [ ] 所有领域规则和权限边界都由后端执行。
- [ ] 库存、金额、状态流转、审计和并发行为符合关联规则。
- [ ] API 文档、OpenAPI 生成类型、后端返回数据与前端使用的数据保持一致。
- [ ] 数据迁移可在空库和已有数据的开发数据库上正常应用。
- [ ] 关键验收场景有自动化测试覆盖。

```

## 给 AI 的文件选择清单

每次开发模块，至少把以下文件放进同一仓库并明确让 AI 阅读。不要只给一句自然语言需求。

| 文件 | 是否必需 | 原因 |
|---|---:|---|
| `docs/功能模块设计.docx` | 是 | 功能范围、首期边界、角色、流程和参考交互的主文档 |
| `docs/system-design.md` | 是 | 已确认的概念、逻辑和数据库设计基线 |
| `README.md` | 是 | 技术栈、目录、启动与项目协作规则 |
| `docs/requirements.md` | 是 | 确定功能范围和不做的内容 |
| `docs/domain-rules.md` | 是 | 防止库存、金额、单据状态和权限实现错误 |
| `docs/data-model.md` | 是 | 防止模型、字段、外键和索引偏离设计 |
| `docs/api.md` | 是 | 保持后端、OpenAPI 与前端类型一致 |
| `docs/ui.md` | 有页面时必需 | 定义列表、表单、详情和状态交互 |
| `docs/acceptance.md` | 是 | 提供可验收的测试目标 |
| 当前模块相关源代码 | 是 | 复用项目已有模式，避免重复实现 |
| 当前模块相关测试 | 是 | 保持既有行为并补充回归覆盖 |
| OpenAPI Schema/生成配置 | 有前端时必需 | 生成客户端与 TypeScript 类型 |
| `.env.example`、Compose 配置 | 初始化或环境变更时必需 | 避免本地运行配置不一致 |

## 每次任务的最小上下文

对于一个已存在的项目，至少提供：功能模块设计、最终系统设计说明书、上述全部 `docs`、本模块后端 app、前端 feature 目录、共享的认证/权限/错误处理/库存服务、相关测试，以及 API/OpenAPI 配置。

对于一个纯后端任务，可以省略 `docs/ui.md` 和前端源码；对于一个纯页面任务，仍必须提供 `docs/api.md`、关联领域规则、OpenAPI 生成类型、相关后端响应示例和当前页面代码。涉及库存、金额、审核、作废、退货、盘点或调拨时，`docs/domain-rules.md`、库存 service 和库存测试绝不能省略。

## 推荐拆分粒度

一次只让 AI 完成一个可独立验收的纵向模块，例如“商品资料管理”“采购单草稿与审核入库”“销售单草稿与审核出库”“盘点调整”“库存流水查询”。不要把全套进销存交给一次任务；也不要把同一个模块拆成先只做模型、再只做 API、最后只做页面，除非项目规模或人工评审需要。优先让每次任务完成一条从页面到 API、业务服务、数据库和测试的完整链路。
